CNL2 — complete Wireshark experiment walkthrough
================================================

Target setup
------------
These menu names are written for the software installed on this computer:

- Ubuntu/Linux
- Wireshark 4.4.8
- Firefox 153

If you perform the lab on another operating system or a materially different
Wireshark version, keep the filters and evidence requirements below, but expect
small changes in button placement.

Important rules before starting
-------------------------------

1. Do the captures yourself. Do not copy measured values, IP addresses, packet
   numbers, timings, passwords, or screenshots from anybody else.
2. The required supplied file `telnet.pcap` is currently missing from `CNL2`.
   Request/download the exact file for Experiment 2 from the course staff or
   course portal before doing section B2 below. The live Telehack capture is not
   a replacement for that supplied file because questions B2.1–B2.3 explicitly
   refer to `telnet.pcap`.
3. Never type a real username or password into Telnet. Telehack is only used for
   harmless public commands.
4. Use one capture file per experiment. Save in legacy pcap format, not the
   default pcapng format, because the grading criteria explicitly require `.pcap`.
5. A screenshot must show enough context to prove the result: keep the packet
   list, selected packet, relevant expanded protocol fields, and display filter
   visible whenever possible. Do not crop away packet numbers, filters, or field
   names.
6. For a screenshot of the active window on Ubuntu, press `Alt+Print Screen` and
   save it with the exact suggested filename. If your desktop opens a screenshot
   dialog, choose `Window`, click Wireshark/Terminal, then click `Capture`.

PART A — Experiment 1: initial HTTP analysis
============================================

A1. Capture the HTTP page load
------------------------------

A1.1 Configure the capture

1. Open Wireshark.
2. Click `Capture` in the top menu.
3. Click `Options...`.
4. In the `Input` tab, click once on the active Internet interface identified in
   step 0.2. Select only that interface. Its `Traffic` sparkline should be moving.
5. Leave the `Capture Filter` field completely empty. A capture filter such as
   `http` would incorrectly remove the DNS and TCP packets needed by the questions.
6. Keep `Promiscuous` enabled for the selected interface.
7. Keep `Snaplen` at the default/unlimited value so image bodies are not cut off.
8. Click the `Output` tab.
9. Enable `Capture to a permanent file` if it is not already enabled.
10. Click the browse button beside `File`, browse to the `CNL2` folder, enter
    `http.pcap`, and click `Save` in the file chooser.
11. In `Output format`, select the entry containing `pcap` (not `pcapng`). In
    Wireshark this is normally displayed as `pcap` or
    `Wireshark/tcpdump/... - pcap`.
12. Do not enable a ring buffer or automatic creation of multiple files.
13. Click `Start`.

Screenshot checkpoint `screenshots/01-http-capture-running.png`:
After clicking Start, capture the Wireshark window while packets are visibly
arriving. The interface/capture status and packet list should be visible.

A1.2 Generate only the intended HTTP traffic

1. Switch to the private Firefox window.
2. Click the address bar.
3. Type this exact URL, including `http://`:

       http://sina.sharif.edu/~azad/

4. Press `Enter`.
5. Wait until the page and its photographs are fully visible and the loading
   indicator stops.
6. Verify that the address bar still begins with `http://`. If Firefox upgrades
   it to HTTPS, click the padlock/shield warning and choose to continue to the
   HTTP site. If HTTPS-Only Mode prevents this, click the three-line Firefox
   menu -> `Settings` -> `Privacy & Security` -> scroll to `HTTPS-Only Mode` ->
   select `Don't enable HTTPS-Only Mode`, then repeat the page load. Re-enable
   your previous HTTPS-Only setting after the capture.
7. Press `Ctrl+Shift+R` once to force a complete reload and ensure the two page
   images are requested during the capture.
8. Wait for the reload to finish.

Screenshot checkpoint `screenshots/02-http-page.png`:
Capture the Firefox window with the complete page, both downloaded images, and
the full `http://sina.sharif.edu/~azad/` address visible.

A1.3 Stop and preserve the capture

1. Return to Wireshark.
2. Click `Capture` -> `Stop`, or click the red square Stop button in the toolbar.

3. Click `File` -> `Save`.

A3. Determine which protocols carry most of the traffic
-------------------------------------------------------

1. Clear the display filter by clicking the `X` at the right side of the filter
   bar. This is essential; statistics otherwise apply only to displayed packets.
2. Click `Statistics` -> `Protocol Hierarchy`.
3. Expand relevant rows using the arrows beside `Internet Protocol Version 4`,
   `Transmission Control Protocol`, and `Hypertext Transfer Protocol`.
4. Read both `Packets`/`Percent Packets` and `Bytes`/`Percent Bytes`.
5. Record the largest protocols separately. Because one packet contains several
   protocol layers, percentages from different layers need not add to 100%.
6. Click the `Copy` button and choose `as CSV` if available; paste the copied
   values into your working notes. Do not use the copied table as a substitute
   for the screenshot.

Screenshot checkpoint `screenshots/04-http-protocol-hierarchy.png`:
Capture the entire Protocol Hierarchy window with the expanded rows and all
packet/byte columns visible. This is the main evidence for Question A3.

A4. Measure HTTP GET to HTTP 200 OK time
----------------------------------------

1. Close the Protocol Hierarchy window.
2. Enter this display filter:

       http.request.method == "GET" || http.response.code == 200

3. Select the first GET for `sina.sharif.edu`.
4. Expand `Hypertext Transfer Protocol` in Packet Details.
5. Find `Response in frame: N`, where `N` is a packet number.
6. Double-click the linked frame number `N` if it is clickable. Otherwise press
   `Ctrl+G`, enter `N`, and press `Enter`.
7. On the selected `HTTP/1.1 200 OK` response, expand
   `Hypertext Transfer Protocol`.
8. Find and record all three fields:

   - `Request in frame`
   - `Response in frame`/the current response frame number
   - `Time since request`

9. The exact answer to the timing question is Wireshark's `Time since request`
   value for that matched response. Record it with its displayed unit/precision.
10. If the first GET did not receive a 200 response, use the first GET that has a
    linked 200 response and state this selection honestly in the report.

Screenshot checkpoint `screenshots/05-http-get-ok-time.png`:

PART C — Experiment 3: DNS request/response analysis
====================================================

C1. Clear the local DNS cache and record resolver settings
---------------------------------------------------------

The assignment's old Linux command restarts the networking service. On this
Ubuntu system, use the narrower cache-only command below so the network remains
connected.

1. Open Terminal.
2. Run:

       sudo resolvectl flush-caches

3. Enter your system password if requested. No output normally means success.
4. Run:

       resolvectl status

5. Find and record the `Current DNS Server` and the DNS servers associated with
   the active interface.
6. Run:

       ip -brief address

7. Record the active interface's local IPv4 address. Also note that Ubuntu may
   send the application's first DNS query to the local stub resolver
   `127.0.0.53`; this is why the DNS capture below uses the `any` interface.

Screenshot checkpoint `screenshots/17-dns-resolver-settings.png`:
Show the active interface, its local IP, and the relevant `Current DNS Server`
lines. Multiple screenshots with `-1`, `-2` are acceptable if needed.

C2. Capture a dig query
-----------------------

1. Return to Wireshark.
2. Click `File` -> `Close` and preserve the previous capture if prompted.
3. Click `Capture` -> `Options...`.
4. Select only the interface named `any`. Capturing on `any` ensures the trace
   includes a query sent to the local loopback stub as well as any upstream query
   visible on the physical interface.
5. Leave `Capture Filter` empty.
6. Click `Output`.
7. Set the file to `CNL2/dns.pcap`.
8. Set `Output format` to pcap, not pcapng.
9. Click `Start`.
10. Switch immediately to Terminal and run:

       dig sina.sharif.edu A

11. Wait for the complete output. Record the `SERVER:` line, status, flags,
    QUESTION SECTION, ANSWER SECTION, and query time.

Screenshot checkpoint `screenshots/18-dns-dig-output.png`:
Capture the complete `dig` result. If it does not fit, capture at least the
header/QUESTION/ANSWER in `-1` and the `SERVER`/Query time lines in `-2`.

12. Return to Wireshark.
13. Click `Capture` -> `Stop`.
14. Click `File` -> `Save` and verify `dns.pcap` exists.

C3. Isolate the DNS packets involving your host
------------------------------------------------

1. Enter this broad filter first:

       dns && dns.qry.name == "sina.sharif.edu"

2. Inspect the source/destination addresses of the query and response.
3. If the query uses the active interface's real IPv4 address, replace
   `YOUR_IP` below and apply:

       dns && ip.addr == YOUR_IP

4. If the application talks to the Ubuntu local stub, use:

       dns && ip.addr == 127.0.0.1

5. Do not type quotation marks around the IP address. The correct Wireshark field
   order is `ip.addr == value`.
6. Identify the query destination IP and the matching response source IP. They
   answer which DNS server received the request and which server returned the
   response at the observed hop. Do not silently replace an observed loopback
   stub address with an upstream address from `resolvectl`; explain both if both
   are relevant.

Screenshot checkpoint `screenshots/19-dns-request-response-list.png`:
Show the host-IP filter, matching query and response rows, packet numbers, source,
destination, protocol, and Info columns.

C4. Analyze the DNS request header
----------------------------------

1. Apply:

       dns.flags.response == 0 && dns.qry.name == "sina.sharif.edu"

2. Select the query packet.
3. Expand `Internet Protocol Version 4` (or IPv6 if actually used).
4. Record source and destination addresses.
5. Expand `User Datagram Protocol` and record source/destination ports. If your
   actual query uses TCP, expand TCP and report that instead.
6. Expand `Domain Name System (query)`.
7. Record `Transaction ID`.
8. Expand `Flags` and record every displayed flag/value, especially:

   - Response (QR)
   - Opcode
   - Truncated (TC)
   - Recursion desired (RD)
   - Z/reserved bits
   - any other flags shown by your version

9. Record `Questions`, `Answer RRs`, `Authority RRs`, and `Additional RRs`.
10. Expand `Queries` and record Name, Type, and Class.

Screenshot checkpoint `screenshots/20-dns-request-header.png`:
Show the query-only filter, selected query, IP/UDP endpoints, transaction ID,
fully expanded Flags, count fields, and expanded Queries. Use `-1` and `-2` if
one screen cannot show all fields legibly.

C5. Analyze the matching DNS reply header
-----------------------------------------

1. Apply:

       dns.flags.response == 1 && dns.qry.name == "sina.sharif.edu"

2. Select the response with the same transaction ID as the query.
3. Expand `Internet Protocol Version 4` (or IPv6) and verify that source and
   destination reverse relative to the request.
4. Expand UDP/TCP and record the ports.
5. Expand `Domain Name System (response)`.
6. Verify and record the same `Transaction ID`.
7. Expand `Flags` and record every value, especially:

   - Response (QR)
   - Opcode
   - Authoritative Answer (AA)
   - Truncated (TC)
   - Recursion desired (RD)
   - Recursion available (RA)
   - Z/reserved bits
   - Reply code (RCODE)

8. Record the four section counts.
9. Expand `Queries` and `Answers`.
10. For every answer resource record, record Name, Type, Class, TTL, data length,
    and returned value/IP. If `Authorities` or `Additional records` are nonempty,
    expand and record those too.

Screenshot checkpoint `screenshots/21-dns-response-header.png`:
Show the response-only filter, selected matching response, IP/UDP endpoints,
transaction ID, fully expanded response flags, and section counts.

Screenshot checkpoint `screenshots/22-dns-answer-records.png`:
Show all expanded Answer records and their Type, TTL, and returned values. Use
numbered continuations if necessary.
